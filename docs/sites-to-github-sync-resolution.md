# Sites → GitHub 직접 업로드 문제 해결 기록

## 1. 문제의 실제 위치

이번 문제는 사이트 소스 코드, 빌드 결과물, GitHub 저장소 존재 여부의 문제가 아니다.

실제 병목은 다음 세 조건이 동시에 겹친 데 있다.

1. Sites 내부 저장소의 `origin`은 GitHub가 아니라 `git.chatgpt-team.site` 내부 원격 저장소다.
2. Sites 실행환경에는 GitHub 원격 저장소로 push할 인증 경로가 없다.
3. Sites 실행환경은 GitHub CLI 또는 github.com 직접 네트워크 접근을 보장하지 않는다.

따라서 `git remote add github ...` 후 `git push github main`으로 해결하려는 방식은 구조적으로 실패한다.

## 2. 원인 정의

문제의 본질은 **저장소 부재**가 아니라 **권한 경계가 다른 두 저장소 사이의 동기화 브리지 부재**다.

```text
Sites 내부 저장소
  - 목적: 사이트 생성·수정·배포
  - 원격: git.chatgpt-team.site
  - 권한: Sites 내부 쓰기 권한

GitHub 공개 저장소
  - 목적: 외부 공개·보존·버전 추적
  - 원격: github.com/GilHaJeong/openai-llm-community-archive
  - 권한: GitHub 커넥터 쓰기 권한
```

두 저장소는 같은 Git처럼 보여도 인증 주체와 네트워크 경계가 다르다. 그러므로 Sites 내부 저장소를 GitHub에 직접 밀어 넣는 방식은 현재 권한 구조에서는 해결 대상이 아니라 회피 대상이다.

## 3. 해결 판단

직접 push 경로를 복구하려면 다음 중 하나가 필요하다.

- Sites 작업환경에 GitHub 원격 등록 권한 제공
- Sites 작업환경에 GitHub 인증 토큰 제공
- Sites 작업환경에서 github.com outbound 네트워크 허용
- Sites가 공식적으로 GitHub export 또는 mirror 기능 제공

현재 사용 가능한 도구 범위에서는 위 조건을 변경할 권한이 없다.

따라서 실질적 해결은 다음 구조로 전환하는 것이다.

```text
Sites 내부 저장소 직접 push ❌

Sites 결과물·정본 문서 추출
  ↓
GitHub 커넥터 기반 파일 생성·갱신
  ↓
GitHub 공개 정본 저장소 유지 ✅
```

## 4. 이번에 확정한 해결 방식

이 저장소는 Sites의 내부 Git 원격 저장소가 아니라, 별도의 공개 보존 원본이다.

앞으로의 기준은 다음과 같다.

1. Sites는 운영·배포 채널로 둔다.
2. GitHub는 공개 보존·외부 모델 접근 채널로 둔다.
3. Sites 내부 Git 원격을 GitHub로 바꾸려 하지 않는다.
4. 공개 가능한 산출물만 GitHub 커넥터를 통해 반영한다.
5. GitHub에는 문제 원인·운영 기준·정본 문서·공개 자료를 남긴다.

- 운영상 우회 동기화 방식 확정: 완료

## 6. 남은 과제

아직 남은 과제는 직접 push가 아니라 **정본 동기화 절차의 반복 운영**이다.

향후 Sites에서 생성된 실제 페이지 원문, 세션 정본, 색인, 공개 필터링 결과물이 확보되면 GitHub 커넥터를 통해 해당 파일들을 같은 저장소에 순차 반영한다.

## 7. 결론

이 문제는 Git 명령 하나로 해결할 문제가 아니라, 서로 다른 권한 경계를 가진 두 저장소를 어떤 기준으로 연결할 것인가의 문제다.

따라서 해결책은 Sites 내부 저장소를 강제로 GitHub화하는 것이 아니라, GitHub를 독립 공개 정본 저장소로 두고 Sites 산출물을 검수 후 반영하는 이중화 구조다.
