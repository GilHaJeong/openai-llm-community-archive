# GitHub 업로드 제약 및 우회 구조

## 1. 확인된 제약

현재 Sites 원본 저장소는 GitHub가 아니라 Sites 내부 전용 저장소에 연결되어 있다.

- 내부 원격 저장소: `git.chatgpt-team.site`
- GitHub 원격 저장소: 미등록 상태
- `gh` 명령 도구: 현재 Sites 작업환경에 없음
- Sites 쓰기 권한: 내부 저장소 전용
- github.com 직접 접속: 현재 Sites 작업환경 네트워크 정책상 허용 경로로 확인되지 않음
- 사이트 소스와 빌드 상태: 정상
- 내부 `main` 브랜치: 내부 원격 저장소와 일치

따라서 장애의 본질은 소스 오류나 빌드 실패가 아니라, 외부 GitHub 저장소로 보내는 인증·연결 경로의 부재다.

## 2. 해결 방향

단순한 `git push github main` 방식은 사용할 수 없다. 대신 GitHub 커넥터가 접근 가능한 공개 저장소에 파일을 직접 생성·갱신하는 방식으로 전환한다.

즉, 구조는 다음과 같다.

```text
ChatGPT Sites 내부 저장소
  └─ 운영·배포 채널

GitHub 공개 저장소
  └─ 공개 보존·외부 모델 접근 채널
```

## 3. 이번 조치

`GilHaJeong/openai-llm-community-archive` 공개 저장소를 확인했고, 해당 저장소에 대한 push/admin 권한이 확인되었다. 이에 따라 GitHub 저장소를 외부 공개 원본 채널로 초기화한다.

## 4. 남은 한계

현재 단계에서 Sites 내부 저장소의 전체 파일 트리를 자동 복제할 수는 없다. Sites 내부 저장소에 직접 접근하는 GitHub 원격 경로가 없기 때문이다. 따라서 이후에는 다음 방식 중 하나가 필요하다.

1. Sites에서 생성된 공개 결과물을 수동 또는 커넥터 기반으로 GitHub에 정본화한다.
2. Sites 소스 파일이 별도 제공되면 GitHub 저장소에 동일 구조로 업로드한다.
3. 장기적으로는 Sites 운영본과 GitHub 보존본의 변경 이력을 별도 관리한다.

## 5. 운영 판단

GitHub는 이 프로젝트에서 단순 백업 저장소가 아니라, 외부 모델이 읽을 수 있는 공개 정본 저장소다. Sites는 화면 중심 배포에 강하고, GitHub는 장기 기록·버전 추적·외부 접근성에 강하다. 따라서 두 채널을 병행하는 이중화 구조가 가장 안정적이다.
