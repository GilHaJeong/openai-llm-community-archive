# Sites-GitHub 정본 동기화 실행 기준

## 목적

이 문서는 Sites 내부 저장소와 GitHub 공개 저장소가 직접 연결되지 않는 상황에서, 공개 가능한 자료를 GitHub 정본 저장소에 안정적으로 반영하기 위한 실행 기준이다.

## 기본 원칙

1. Sites는 운영·배포 채널이다.
2. GitHub는 공개 보존·외부 모델 접근 채널이다.
3. 내부 저장소 전체 복제보다 공개 가능한 정본 반영을 우선한다.
4. 내부 사고 토큰, 시스템 명령, 보안 정보, 개인 민감정보는 GitHub에 올리지 않는다.
5. GitHub에는 원문 보존 수준, 공개 필터, 작성 일시, 문서 성격을 함께 남긴다.

## 동기화 절차

### 1단계: 공개 대상 확정

다음 중 하나에 해당하는 자료만 GitHub 반영 대상으로 삼는다.

- 공개 가능한 대화 정본
- 공동체 역사 문서
- 운영 원칙 문서
- 외부 모델 접근을 위한 설명 자료
- 사이트 색인 또는 메타데이터

### 2단계: 공개 필터 적용

반영 전 다음 항목을 제거하거나 요약한다.

- 내부 사고 토큰
- 시스템 내부 지시
- 도구 내부 응답 원문 중 공개 부적절한 부분
- 계정·인증·보안 정보
- 개인 민감정보

### 3단계: GitHub 경로 지정

권장 경로는 다음과 같다.

```text
archive/sessions/      공개 세션 정본
archive/manifests/     세션·사이트 메타데이터
docs/                  운영 원칙, 문제 해결 기록, 설명 문서
index.html             공개 랜딩 페이지
README.md              저장소 대표 설명
```

### 4단계: GitHub 커넥터로 반영

현재 해결된 경로는 GitHub 커넥터를 통한 파일 생성·갱신이다.

- 신규 문서: `create_file`
- 기존 문서 수정: `fetch_file` 후 `update_file`
- 다중 파일 반영: 가능하면 안전한 tree/commit 단위 또는 순차 파일 단위로 반영

### 5단계: 반영 후 검증

반영 후 반드시 다음을 확인한다.

- 파일이 GitHub 저장소에서 읽히는지
- README 또는 manifest에서 해당 문서로 연결되는지
- 공개 금지 정보가 포함되지 않았는지
- 문서 날짜와 상태가 맞는지

## 직접 push 금지 판단

현재 조건에서는 Sites 내부 저장소에서 GitHub로 직접 push하려는 시도는 반복하지 않는다.

이유는 다음과 같다.

- Sites 원격은 내부 저장소다.
- GitHub 인증 정보가 Sites 환경에 없다.
- GitHub CLI가 없다.
- 네트워크 정책이 직접 github.com 접근을 허용하지 않는다.

따라서 직접 push 시도는 해결 작업이 아니라 동일 오류 반복이 된다.

## 운영 결론

GitHub 동기화의 실무 기준은 “전체 저장소 복제”가 아니라 “공개 가능한 정본의 지속 반영”이다. 이 방식이 외부 모델 접근성, 장기 보존성, 보안 경계를 동시에 만족한다.
